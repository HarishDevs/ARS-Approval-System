ARS Approval Platform Plan

Main purpose: multi-level approvals in any custom manner. Unlimited levels, combined freely as sequential, parallel, any-one, any-N-of-M, conditional or hybrid, with approvers from any source. One approval engine replaces the 104 Asana approval projects. This plan combines the development plan you shared with your requirements:

  • an Admin Portal (Super Admin)
  • Google sign-in, or password + OTP
  • new-login alerts
  • email and WhatsApp for every notification
  • no backend visibility for anyone except the Super Admin

New-login alert

A sign-in counts as new when the device is not recognised (a signed device cookie plus browser and OS) or the network location changes sharply. The alert goes to both email and WhatsApp. Alerts also go out for password changes, OTP channel changes, lockouts and repeated failed attempts. Every Super Admin sign-in also triggers one.

ARS Approvals: New sign-in to your account 28 Sep 2026, 15:32 · Chrome on Windows · near <city> · IP 49.xx.xx.xx If this was you, no action is needed. If not, tap to sign out everywhere and lock your account: <secure link>

"This wasn't me" ends every session, locks the account, and notifies the Super Admin.

Keeping the backend hidden

Goal: apart from the Super Admin, no user can learn which providers, APIs, configuration or infrastructure the platform uses.

LayerControl
Admin PortalSeparate app and address, not linked from the main app. The server checks the Super Admin role on every call. Step-up OTP for sensitive changes. Optional office-IP allowlist
User app codeBuilt separately from the Admin Portal, so no admin screens or admin API paths are shipped to users. No source maps, no configuration or keys in the browser. Feature flags are decided on the server
APINo public API documentation. Every call needs a signed-in session, and permission is checked on the server for each record. Admin routes are blocked for anyone else before they reach the app. CORS allows only ARS addresses. Rate limits apply
ResponsesGeneric error messages and reference codes instead of stack traces. Server and framework headers removed. No provider names in pages or messages
Emails and WhatsAppSender shown as "ARS Approvals". No provider branding or tracking domains visible where avoidable
SecretsHeld in a server-side secret store, encrypted at rest. Shown masked even in the Admin Portal. Rotated at go-live and on a schedule
LogsUsers see only the business timeline of their requests. Technical logs and errors are visible only in the Admin Portal
Infrastructure accountsHosting, database, domain/DNS, Google Cloud (OAuth), WhatsApp provider and email service are all owned by itadmin@arssteels.co.in with 2-step verification
One limit to plan for. Whoever builds and hosts the system has technical access while building it. That includes developers, the hosting provider's staff, and anyone given server access. Cover it with time-limited access for developers, an NDA, a handover checklist, and rotating every key and password at go-live so only the Super Admin holds them afterwards.

What a DoA matrix is

A Delegation of Authority (DoA) matrix is one table, signed off by management. For each kind of request and each amount range, it says who must approve, and in what order. The engine reads it to choose the approval levels automatically. Today there is none: one approver clears everything from ₹3,890 to ₹5 Cr.

The example below uses today's approvers. The amounts and names are placeholders for management to fill in.

Request typeUp to ₹1 L₹1 L – ₹5 L₹5 L – ₹25 LAbove ₹25 L
Purchase / Work OrderSCM HeadSCM Head → FinanceSCM Head → Finance → EDSCM Head → Finance → ED → MD
Bill / payment / funds transferFinance checker → Finance HOD+ Finance Head+ ED+ MD
HR payments (salary, statutory, F&F)HR Manager → HR HODHR Manager → HR HOD+ Finance → ED+ MD
IT purchase / licence / budgetIT HeadIT Head → Finance+ ED+ MD
Price realisation / discountsDept HOD(s) → EDDept HOD(s) → EDDept HOD(s) → ED → MDDept HOD(s) → ED → MD
Policy / special / investmentEDED → MDED → MDED → MD

Management decides four things:

  1. The amount bands.
  2. The approver roles for each cell.
  3. Whether a department's own HOD always comes first.
  4. Who may approve on someone's behalf.

The developers then enter the table in the Admin Portal. Changes are versioned with effective dates.
