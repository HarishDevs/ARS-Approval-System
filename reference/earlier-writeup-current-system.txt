9. The Most Important Finding

There is an important distinction between the visible workflow and the actual automation logic.

Asana automations can contain:

Trigger → Conditions → Actions

and actions can move tasks between sections, change fields, assign users, create tasks/subtasks, etc.

Therefore, from the project data I can establish:

What the workflow is designed to accomplish.

But I cannot yet establish with certainty:

Which exact Automation moves the task from A → B, which Automation assigns the person, and which Automation marks/completes the task.

The current MCP read-only connector exposes the project, tasks, fields, sections and approval statuses, but not the project's Automation/Rule definitions.

The IT Internal Approval, Finance Internal Approval, and Price Realisation Approval are particularly useful reference models because they demonstrate three different workflow patterns:

IT:
HOD → ASSIGNMENT → EXECUTION → COMPLETION

FINANCE:
LEVEL 1 → LEVEL 2 → HOD → FINAL

PRICE REALISATION:
PENDING → ED → MD → FINAL

These three patterns can serve as the foundation for the single interconnected Approval Platform you are planning.

The future system should therefore not recreate the current projects one-by-one. It should create one configurable Approval Engine capable of reproducing all of these workflows through configuration.

This gives you the current-state company approval architecture without depending on the Rules/Automation layer. It also gives you the base architecture for the custom interconnected approval platform you described earlier.
